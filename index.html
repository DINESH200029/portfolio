The full story — 6 chapters
1
The problem
Shopify Magic was generating product descriptions using a fine-tuned LLM — but nobody had a rigorous way to know if a new checkpoint was actually better or worse than the last one.
2
Building the test set
I built 1,200 real merchant queries covering product-description and Sidekick use cases — diverse enough to catch regressions across categories, not just average performance.
3
The RAG pipeline
Each query passed through a retrieval agent pulling relevant merchant docs, combined with a Redis cache layer serving repeated patterns in under 360ms — cutting unnecessary LLM calls entirely.
4
Three-track evaluation
Every model output ran through three independent tracks: tone consistency, factual accuracy, and latency benchmarking at p50 and p95.
5
The safety gate
Results fed into a CI regression gate — if any eval metric degraded, the new model was automatically blocked from promotion. This reduced reliance on repeated manual review and made regressions easier to identify.
6
The result
p95 latency dropped from 480ms to 360ms — a 25% improvement. Model releases became provably safer and the evaluation workflow helped make model and prompt-version comparisons more consistent during release-readiness reviews.
System pipeline
INPUT Merchant prompt + Knowledge base
RETRIEVE Embedding model → Sidekick RAG
GENERATE Redis cache / LLM LoRA
GUARD Output guardrails
EVALUATE Tone eval → Fact eval → Latency eval
SHIP Dashboard sync + CI gate

// UBER DRIVER MATCHING
The full story behind the work
The 3 key things I did
1
Contributed to XGBoost driver-matching model
Built on Michelangelo — Uber's internal ML platform — scoring driver-rider pairs in under 50ms at global scale across millions of daily matches.
2
Migrated features from Hive batch to Flink streaming
Reduced feature freshness lag from hours to under 5 minutes — the model finally saw real-world conditions as they actually were.
3
Ran A/B experiments with guardrail metrics
Every model update validated against acceptance rate, cancellation rate, and ETA error. If any degraded, the new model did not ship.
The full story — 6 chapters
1
The scale
Every second, millions of riders and drivers send signals — location pings, trip requests, ETA estimates. The challenge: scoring driver-rider pairs using proximity, acceptance-history, and trip-context signals in high-volume marketplace workflows.
2
The ranking model
I contributed to an XGBoost driver-matching ranking model on Michelangelo. It scored every possible driver-rider pair and surfaced the best match based on dozens of real-time features.
3
The data freshness problem
Features like driver density and demand surge were computed overnight in Hive batch jobs — meaning the model sometimes worked with data hours old. In a live marketplace, that is a real problem.
4
The Flink migration
I helped migrate demand and supply features from overnight Hive jobs to near-real-time Apache Flink streaming pipelines. Feature freshness went from hours of lag to under 5 minutes.
5
Proving it worked safely
Ranking-model updates were evaluated through A/B experiments and guardrail tracking. We tracked acceptance rate, cancellation rate, and ETA error as guardrails. If any degraded, it did not ship.
6
The outcome
Fresher features meant better matches. The pipeline that once took hours now responded in minutes — improving match accuracy across millions of daily rides.
System pipeline
INGEST Ride requests + Driver status + ETA signals
STREAM Kafka event bus → Flink streaming
FEATURES Palette feature store → Feature engineering
MODEL XGBoost ranker Michelangelo · <50ms
VALIDATE A/B experiment → Metric tracking → Guardrail gate
DEPLOY Global rollout Michelangelo serving
